# 每份产物回答什么问题

> **判据只有一句：这份文档有没有一句话，是别处答不了的？**
> 没有 → 合并或删掉。文档越多，维护成本越高，而且**重复的内容会分叉**（改了 A 忘了 B，两边说法不一致）。

---

## 一、先看一个真实的失败案例

《以日为鉴》Ep00 第一次交付时，集目录里同时有 3 份文档：`调研材料.md`、`视频分镜脚本.md`、`运镜与制作思路.md`。

事后逐条比对，发现：

| 重复项 | 重复次数 | 真源本应是 |
|---|---|---|
| 字幕金句 | **30/34 条被原样抄了两遍**（分镜脚本 + SRT） | `字幕.srt` |
| 呈现/动效规则（文字整块淡入、并列整组给…） | 抄了 2 遍（制作思路 + skill 的 presentation-rules） | `series-video-planner/references/presentation-rules.md` |
| 幕的时间码与时长 | 抄了 **4 遍**（分镜表、SCENES 数组、SRT、制作思路） | `framework.js` 的 `SCENES` 数组 |
| 制作红线 | 抄了 2 遍（调研材料 + 分镜脚本） | 两份都有用，但**正文只能有一份**，另一份只留指针 |

**为什么会这样**：不是懒，是每次改版都往"最顺手的那份"里加内容。加着加着，三份文档长成了同一个东西。

**后果不只是冗余**：Ep00 修数字时，我改了卡片、改了字幕第 2 条，**漏了字幕第 3 条**——因为同一个事实散落在 3 处，改的人记不住。漏掉的那处差点跟着成片发出去。

## 二、五份产物，五个不可替代的问题

| 产物 | 回答的问题 | 谁来看 | 真源 |
|---|---|---|---|
| `调研材料.md` | **这个数字从哪来？可信吗？什么口径？** | 做这一集的人、审稿的人 | 硬数字表 |
| `视频分镜脚本.md` | **每一幕承重什么？观众带着什么离开？** | 做这一集的人、审分镜的人 | 幕意图 |
| `运镜与制作思路.md` | **为什么这么设计？踩过什么坑？** | 接手的人、想模仿的人 | 设计决策 |
| `字幕.srt` | **说什么话？什么时候说？** | 配音、后期、审校 | 字幕正文 |
| `发布文案.md` | **发出去时标题写什么、正文写什么、挂什么话题？** | 自动发布引擎、运营的人 | 机读 JSON 块 |
| `系列风格总纲.md` | **画风/视频/封面有哪些通用规则？** | 全系列所有集 | 风格规则 |

### 判断某段内容该放哪

```
这段内容会不会对别的集也成立？
├─ 会  → 上提到 系列风格总纲.md / style-tokens.json（集目录只留指针）
└─ 不会 → 它回答的是哪个问题？
         ├─ 这个数字对不对     → 调研材料
         ├─ 这一幕要干什么     → 分镜脚本
         ├─ 为什么这样设计     → 制作思路
         ├─ 具体说什么话       → 字幕.srt
         └─ 怎么发出去         → 发布文案
```

## 三、各文档的边界（写之前先看"不写什么"）

### `调研材料.md`

**写**：核心问题（这集要回答什么）、人话版概念（每个配一个类比）、**硬数字表**（值 / 原文出处 / 核实状态）、金句候选、候选叙事线、⚠️ 勘误与争议红线。

**不写**：字幕全文、时间码、画面细节。

**关键纪律**：硬数字表的每一行都必须能追到原文某一句。**查不到的写"约/示意"，绝不写精确数字**。

**⚠️ 顺序纪律（血的教训）**：**必须先写这份，再写分镜、再写代码**。
Ep00 是"先出片后补文档"，结果钩子里凭印象写的两个数字（"东京地价买下整个美国""日经 38,957 点"）**书里根本不存在**，一路漏进画面和字幕。补文档时才查出来。
**写钩子时凭常识印象填数字，是整条链路上最高危的一步。**

---

### `视频分镜脚本.md`

**写**：8 幕边界表（时间码 / 幕名 / **画面要点一句话** / **字幕条号**）、系列元素三件套、本集特有的红线、实际实现与文档的差异。

**不写**：
- ❌ **字幕全文** → 只写 `(#12)`，正文在 `字幕.srt`
- ❌ **"为什么这么设计"** → 那是制作思路的事
- ❌ **动效参数、色值、字体** → 那是风格总纲与引擎的事
- ❌ **数据出处** → 那是调研材料的事

**表长什么样**：

```markdown
| 幕 | 时间码 | len | 画面要点（一句话） | 字幕（条号） |
|---|---|---|---|---|
| S2 钩子 | 00:12–00:30 | 18 | 1989/1999 双卡对抗，中间朱红断言 | #2–#5 |
```

> 时间码只是**方便人读的镜像**，真源是 `framework.js` 的 `SCENES` 数组。改时长先改 SCENES，再同步这张表。

---

### `运镜与制作思路.md`

**写**：这一集的定位（一句话 + 它不是/它是）、**本集特有的**节奏决策、**逐幕为什么这么画**、母题使用频率、**踩过的坑（症状 → 根因 → 修法）**。

**不写**：
- ❌ **通用风格规则**（呈现原则、动效白名单、布光、版式）→ 上提到 `系列风格总纲.md`，这里只留指针
- ❌ **分镜表**（时间码+画面+字幕）→ 分镜脚本的事
- ❌ **数据出处**

**"踩坑记录"是这份文档最值钱的部分**：它把排错经验传给下一个人。没有这一节，接手者会把同样的坑再踩一遍。格式统一为：**症状 → 根因 → 修法**。

---

### `字幕.srt`

**唯一真源**。voice-ready 规范（5.0 字/秒、单条 12–24 字、槽位 2.6–4.5s、幕边界落字幕边界）见 SKILL.md 的 Voice-ready 字幕规范。

**不写**：任何解释性内容。SRT 里只有编号、时间、文字。

---

### `发布文案.md`

**回答**：这一集发出去时，标题写什么、正文写什么、挂什么话题？

**为什么必须有这份**：抖音的标题是**创作决策**，不是提取任务——字幕是叙述性的，标题要是钩子。没有这份文档，标题只能从"分镜脚本的钩子文案 / 变更记录的主旨 / 集目录名"临时拼（这是 `douyin-publisher` 的降级链），结果就是现有 35 集的样子：**标题被去标点、没有正文、话题靠猜**。

**写**：标题候选（含选择理由）、定稿标题、正文、话题、以及一段 `## 机读` 的 JSON。

**不写**：字幕全文、画面描述、数据出处。

**硬限制（抖音平台）**：

| 字段 | 限制 | 本系列口径 |
|---|---|---|
| 标题 | **硬限 30 字**（超了工具 `title[:30]` 截断） | 10–16 字 |
| 正文 | 短，手机右侧文案区 | 40–70 字，2–3 行 |
| 话题 | 总数 ≤5，第 1 个是系列名 | 1 + 2–4 |

**机读块与 publisher 的衔接**：`douyin-publisher` 吃 manifest 的 `text` 字段，格式是「第一行=标题 / 中间=正文 / 末尾=#话题」。**不要让文案在两处分叉**——用脚本从 `发布文案.md` 的 `## 机读` JSON 生成 manifest，不要手抄（Ep00 吃过"字幕抄两遍、修数字漏一处"的亏）。

**标题怎么想**（三种套路，与钩子同源）：反常识断言 / 数字落差 / 一句话扎心。
**检验法**：念给没看过的人听，他会不会问"为什么？"——会就是钩子，不会就是陈述句。

**流程位置**：`调研 → 分镜 → 代码 → 成片 → 发布文案 → 发布`。放最后是因为此时内容定稿、最清楚哪句最抓人；但不能省。

---

### `系列风格总纲.md`

**写**：从主旨推导风格的过程、母题、色板、字体、版式、八条铁律、幕结构模板、封面策略、DoD、反例清单。

**不写**：任何单集的内容。

**上提判据**：一段内容如果"对下一集也成立"，就不该躺在集目录里。

---

## 四、可以删掉的东西（止损清单）

做完一集后，对照检查：

| 症状 | 处理 |
|---|---|
| 集目录里有第二份"风格规则" | 删掉，改成指针 |
| 分镜脚本里贴了字幕全文 | 删掉，只留条号 |
| 同一个数字在 3 个文件里各写一遍 | 只留 `调研材料.md`，其余引用 |
| 某份文档只有"这次做了什么"没有"为什么" | 合并进另一份，别单独立文件 |
| 某份文档 90% 内容抄自 skill 的 reference | 删掉，直接读 skill |
| 一份文档改了三版还是没人看 | 它没回答任何人的问题，删 |

## 五、文档数量怎么定

**不是固定 3 份或 5 份，是按需**：

| 场景 | 最少需要 |
|---|---|
| 一次性的单集视频 | `调研材料.md` + `字幕.srt`（够自己用） |
| 要交给别人做的系列集 | 五份全要（别人需要知道为什么、数据从哪来、规则在哪） |
| 已有成熟样板、只是照抄格式 | `调研材料.md` + `字幕.srt` + 分镜表（为什么可以口头说） |
| 快速试错的原型 | 什么都不写，代码即文档 |

**判断法**：**你希望接手的人知道多少，就写多少**。他要能追溯数据 → 调研材料；他能独立审设计 → 分镜脚本；他想改得更好 → 制作思路。

---

## 六、一句话总结

> **文档不是交付物，是沟通渠道。**
> 每份文档都该有一个明确的收件人，和一个他别处得不到的答案。
> 没有收件人的文档，写的时候很爽，维护的时候是债。
